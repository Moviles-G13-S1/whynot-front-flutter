# Smart Recommendation result cache — Santiago Casasbuenas

The Flutter app shares one `RecommendationController` through `AppDependencies`. It now has two levels for the catalog. `RecommendationCatalogSnapshotCache` holds **one** authenticated user's complete catalog for **5 minutes**, or an empty catalog for **30 seconds**. This avoids another database-backed callable on a quick revisit and does not need LRU bookkeeping because only one user's catalog is retained. `RecommendationResultCache<CatalogProductDetails>` separately holds the **five most recently opened products' display fields** for **5 minutes**. Its key combines authenticated UID and source product ID. The Home top pick keeps its separate 8-entry UID-keyed LRU. Errors and saveable recommendation event IDs are not cached. None of these entries survive an app restart.

The catalog snapshot is keyed by UID because the list request has no explicit parameters. Opening a product for the first time fetches full details and creates one saveable recommendation event. Reopening a product in the detail LRU sends `eventOnly: true`; the backend still rechecks eligibility and creates a **new** event, while Flutter uses its cached display fields. A hit moves that product to the newest position; opening a sixth distinct product evicts the oldest. The controller clears all entries on sign-in, account creation, sign-out, and an observed user switch. It rejects old in-flight results after a user switch or invalidation. Concurrent ordinary catalog requests share one backend call. Explicit Refresh bypasses the snapshot and replaces it only after success, so a failed refresh leaves a valid previous snapshot available to a later ordinary lookup.

Successful local product create/update/delete/purchase, demographic-profile update, wishlist create/delete, and recommendation save invalidate the catalog snapshot, detail LRU, and Home pick. Changes made on other devices are not locally observable, so the **5-minute TTL** bounds catalog and display-data staleness, while every product open still checks server eligibility. The 30-second empty-catalog and null-top-pick TTLs let newly eligible products appear sooner. This cache does not implement offline display or network recovery; that is Sprint 3 point 3.

`RecommendationCacheStats` exposes hit, miss, eviction, expiration, and coalescing counts without product or user data. `flutter test test/recommendation_cache_test.dart` demonstrates the cold/warm path: **cold = 1 callable; warm = 0 callables**. It also tests LRU order, TTL boundaries, user isolation, in-flight deduplication, force refresh, and mutation invalidation. A physical-device cold/warm demonstration is still needed.

The Home button opens a recommendation catalog. Its source label distinguishes a fresh list fetch from a cached catalog snapshot, and Refresh deliberately fetches again. A small gray dot at the bottom-right of a card means that product's display fields occupy one of the five detail-LRU slots. Listing the catalog alone does not add dots or create `recommendation_shown` events. Results cover the user's preferred category and categories represented by saved products, interleaved across categories. Mounted Home and catalog views reload after successful local changes. The backend currently gathers the whole eligible list in one request; a larger collection needs pagination and a response-size policy. The updated `get_recommendation` callable with `eventOnly` support was deployed to `whynot-f4ae6` on October 26, 2026; both recommendation callables report `ACTIVE`. A signed-in device check remains.

## Product images

The Home card and detail view currently use `Image.network` with a fallback, and Flutter's in-process image cache can reuse the same image provider URL between those views. We evaluated `cached_network_image` but did not add it for this result-cache change: its disk cache and extra dependency would add a separate persistence policy, while this work is deliberately an in-memory recommendation-data cache. `Image.network` does not guarantee an image will be available offline after an app restart. If point 3 needs persistent offline images, evaluate the package there with disk-size, eviction, privacy, and error-state requirements.

The open BQ Home-card instrumentation branch must retain its rule that a cached card becoming visible is a new Home exposure when integrated. Cache hits flow through the same `SmartRecommendationSection` card rendering path.
