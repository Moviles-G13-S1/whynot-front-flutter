# Recently viewed recommendations

Implemented by Santiago Casasbuenas for Sprint 3 local storage.

**Recently viewed** is visible on Home, above **Your Wishlists**. It shows an empty message until the signed-in account has browsing history, then shows up to five distinct catalog products from this installation. To discover recommendations, select **Explore recommendations** on Home to open **For you**. A product enters history when its catalog detail is confirmed by the backend. Reopening a history entry moves it to the top as soon as its local snapshot can be read, including offline. If the backend later responds, its display fields update that visit in place. Opening a sixth distinct product evicts the oldest visit.

After a restart with the same Firebase session, history is available even if the catalog has never loaded in the new process. A history detail shows **Details may be outdated** while only the snapshot is available. Save is disabled until the existing catalog eligibility check returns a fresh event for that product. Reconnection triggers the check on an open detail screen. If the backend check fails while transport is available, **Check availability** retries it. A deleted or newly ineligible source can still appear in local history until it is cleared or evicted. A failed check keeps Save disabled.

**Clear history** deletes the signed-in account's history on this installation. A successful profile-form update or owned-product create, edit, deletion or purchase also clears that account's history because demographic inputs, category membership and duplicate filtering can alter eligibility across several products. A wishlist-only change or recommendation save uses the existing recommendation cache invalidation. Signing out hides the rows and discards open details. Signing back into the same account can restore its rows. A different account sees its own history.

## Storage and integration

- `WhyNotLocalDatabase` owns one lazy connection to the existing `whynot_product_drafts.db`. Production injects that owner into both `SqliteProductDraftStore` and `SqliteRecentRecommendationStore`. The v2-to-v3 migration adds `recent_recommendations` and its recency index. A v1 database first runs the original draft-scope migration and then receives the history table. Both upgrades run inside the SQLite migration transaction.
- Each row stores the UID, source product ID, open timestamp and display fields. A unique UID/product constraint and generated SQLite order support deterministic replacement and eviction, even if two visits have the same wall-clock timestamp. The insert and per-UID trim run in one transaction. A late refresh only updates the visit it belongs to and cannot restore a cleared or evicted row.
- `RecommendationController` reads history through the local store contract. Home loads history independently of the network catalog. Invalid rows are skipped, and a SQLite error leaves the live catalog and eligibility flow usable.
- History contains no authentication credentials or saveable recommendation event IDs. The store performs no Firestore writes and issues no Home exposure or open events. Live eligibility checks and saves use the existing backend paths. The separate five-product [detail LRU](recommendation_cache.md) continues to optimize repeat opens.

## Restart demonstration

1. Sign in online using an account with eligible recommendations. Open at least two different products from **For you**. Wait for each detail's availability check to finish, then return to Home. Confirm the most recent product appears first in **Recently viewed**. If the catalog has six eligible products, open six to demonstrate eviction.
2. Leave the account signed in. Force-quit WhyNot, enable airplane mode and relaunch. Confirm the order persists in **Recently viewed** on Home while the device is offline.
3. Open a history item. Confirm its product text, the outdated notice and disabled **Save this product**. Go back and confirm the item's new position at the top.
4. Open the item again and restore network access. Confirm Save remains disabled through the availability check and becomes usable only if the backend returns a fresh event. To demonstrate account isolation, sign out and sign in online with a different test account. Its history should reflect its own visits. Use **Clear history** on a test account to demonstrate local deletion.
5. To demonstrate the upgrade on an installed v2 build, populate both a general draft and a wishlist draft before installing the v3 build over it. Confirm both drafts are still present after launch and after browsing or clearing history.

On November 25, 2026, `flutter analyze --no-pub` reported no issues, the 33 focused tests passed, and all 161 Flutter tests passed. The FFI tests exercise actual SQLite files, including closing and reopening the database and creating a new store/controller. Widget tests simulate offline and backend recovery through the Home history section. These checks use fakes for Firebase and connectivity. A physical-device restart and airplane-mode demonstration remains pending. Images use the existing network image and fallback, so product text can be available when the image is unavailable. History belongs to this installation and depends on a restored sign-in session. App-data removal, uninstall, or clearing the web origin's storage removes the corresponding local data.
